# Unit 6 — Tech Stack Decisions (Optional Accounts)

**No new tech stack, library, or service is introduced.** Every NFR requirement in
`nfr-requirements.md` §1-2b, §3-8 is satisfied entirely within the existing stack (including the
four founder-review corrections — CSRF, Vercel-aware rate limiting, transaction-safe conflict
handling, and the `account_order_links(account_id)` index), reusing existing, already-reviewed
primitives rather than adding new infrastructure.

| Surface | Decision | Rationale |
|---|---|---|
| Token generation/hashing (§1) | Reuse `generateAccessCredential()`/`hashToken()`/`resolveByAccessToken()` from `src/report-access/credential.ts` unchanged, for both `MagicLinkToken` and `AccountSession` tokens. No new crypto library, no new token format. | These primitives are already generic (parameterized by a caller-supplied store), already reviewed, and already load-bearing for `reportAccessCredentials` — introducing a second token-generation routine for functionally identical needs (high-entropy, hash-only-persisted, single-use-capable bearer tokens) would be pure duplication. Matches the founder's own Q1 instruction: "no general auth platform unless the design proves the existing stack genuinely cannot support the requirement" — it can, and does. |
| Session cookie transport (§2) | Add one new cookie constant, `ACCOUNT_SESSION_COOKIE`, to the existing `src/shared/cookies.ts`, with the exact same `HttpOnly`/`Secure`/`SameSite=Lax` attributes and clear/set helper conventions `CHECKOUT_SESSION_COOKIE`/`REPORT_ACCESS_COOKIE` already use. No new cookie library, no new session-management framework (e.g. no `next-auth`/`iron-session`/JWT library). | `shared/cookies.ts`'s own design comment already states its philosophy generalizes beyond the two cookies it governed at the time it was written ("the cookie is a transport, not a new trust boundary... each caller re-validates... on every request") — Unit 6 is the intended third application of that same pattern, not a reason to introduce a new one. |
| Persistence (all new tables) | Extend the existing Drizzle schema (`src/db/schema.ts`) with 4 new tables (`accounts`, `magic_link_tokens`, `account_sessions`, `account_order_links`) via the existing migration tooling (`src/db/migrations/`), including one new `CHECK` constraint (`magic_link_tokens_purpose_shape_valid`) using the same pattern Unit 5 established for discriminated-shape enforcement. No new ORM, no new migration framework, no new database. | Matches every prior unit's own precedent — this project has never introduced a second persistence mechanism. The `CHECK`-constraint-for-discriminated-shape pattern is now used a second time (first: Unit 5's `screening_requests`/`regulatory_rules` constraints), reinforcing it as a reusable project convention rather than a one-off. |
| CSRF protection (§2b) | Reuse the same-origin CSRF **pattern** Unit 3 established (`src/admin-auth/csrf.ts`'s `checkSameOrigin`: `Sec-Fetch-Site` cross-site rejection, exact `Origin` match, `Referer`-origin fallback, fail-closed) for `AccountSession`-authenticated mutating routes (NFR-U6-51), sharing the underlying non-admin-specific trusted-origin resolution `resolveExpectedAdminOrigin()`/`resolveAppBaseUrl()` already provides (`src/shared/app-url.ts`) rather than admin credentials or admin code. No new CSRF-token framework, no new library. | **Corrected per founder review** — `SameSite=Lax` alone is defense-in-depth, not a complete authorization boundary, and Unit 6 is this project's first customer-facing cookie-authenticated mutation surface. Unit 3's CSRF check is already a generic, non-admin-specific origin-resolution mechanism in practice (despite its name) — reusing its pattern is the same "extend an existing primitive to a second use" discipline this document applies everywhere else, not new infrastructure. |
| Transactional integrity (§4) | Reuse the existing `neon-serverless`-`Pool`-scoped-per-request interactive-transaction pattern Unit 2B introduced for `BR-U2B-15`'s atomic multi-table fulfillment, applied to `verifyLoginLink`'s LOGIN transaction (NFR-U6-27) and `deleteAccount`'s deletion transaction (NFR-U6-32), with `Account`/`AccountOrderLink` conflict handling implemented via `INSERT ... ON CONFLICT DO NOTHING RETURNING ...` + a follow-up `SELECT`, or an explicit `SAVEPOINT` (NFR-U6-28/29 — **corrected per founder review**: a raw caught `UNIQUE` violation cannot be relied upon to leave the enclosing transaction usable). No new transaction/ORM abstraction, no new database driver — `ON CONFLICT`/`SAVEPOINT` are both standard Postgres/Drizzle capability already available today. | Unit 2B already solved "I need a real interactive multi-statement transaction on a serverless platform" for exactly this class of problem — Unit 6's two new transactional operations are additional *uses* of that already-approved mechanism, not a new one; the conflict-handling correction uses only standard SQL capability, not a new dependency. |
| Rate limiting / abuse resistance (§6) | **Corrected per founder review**: primary/outer control is a **Vercel Firewall rate-limiting rule** (NFR-U6-37), configured — not coded — against this project's existing Vercel Pro plan; `FailedLookupRateLimiter` (`src/report-access/rate-limiter.ts`) remains as application-local defense-in-depth only (NFR-U6-38), in its existing, unmodified failure-counting mode, no longer described as the deployment-wide control. No Redis, no distributed rate-limiter, no CAPTCHA, no new security vendor. | The original in-process-only design relied on a stale single-replica assumption; on Vercel, in-process memory is not shared across function instances and is reset by cold starts, so it cannot alone provide deployment-wide enforcement. The corrected model uses Vercel's own already-available platform capability as the outer control — genuinely no new vendor/service, since it's already part of the existing Pro plan — with the existing in-process class demoted to its appropriate role (local defense-in-depth), matching the founder's explicit instruction not to introduce Redis/a distributed service/CAPTCHA. |
| Email delivery (§7) | Reuse `createResendClient()`/`sendEmail()` (`src/email-delivery/resend-client.ts`) unchanged, for two new email templates (login-link, claim-link) alongside the existing report-ready template. No new provider, no new adapter, no bounce/complaint-webhook infrastructure. | Matches Unit 2B's own already-established `EMAIL_SENT`-means-provider-accepted-not-delivered posture (§7's NFR-U6-42) exactly — Unit 6 extends what the adapter is used *for*, not what it *is*. |
| Index (§8) | Add one standard B-tree index on `account_order_links(account_id)` (NFR-U6-57) via the same existing Drizzle migration tooling as every other schema change in this project. No new indexing technology. | Postgres does not automatically index a merely foreign-key-shaped column — `order_id`'s own `UNIQUE` constraint provides no lookup path for `account_id`-filtered queries (`listReportHistory`, NFR-U6-47), a real omission NFR review caught in the schema this document's requirements assume. |

**No new numeric limits are invented (§6/NFR-U6-40)** — the application-local layer reuses
`DEFAULT_RATE_LIMITER_OPTIONS` (`maxFailuresPerWindow: 10`, `windowMs: 60_000`, `cooldownMs:
60_000`) as-is from `src/report-access/rate-limiter.ts`; the Vercel Firewall rule intentionally
reuses the same 10-per-60-seconds shape as initial tuning, explicitly subject to retuning from real
deployment evidence rather than treated as precisely correct today. Any future evidence-driven
retuning of either layer specific to account-auth endpoints is an explicitly deferred follow-up,
not a decision made in this document.

**No new observability, identity, or session-management product is added** — session resolution
and rate-limiting both reuse existing, already-instrumented mechanisms; no new logging framework,
metrics product, or identity provider is introduced (NFR-U6-50).
